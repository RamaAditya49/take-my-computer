# take-my-computer: design and plan

Date: 2026-10-21. Owner: Rama Aditya (RamaAditya49).

## Intent

Give an AI agent full control of a real Linux desktop through MCP.
The agent must see the screen, read it, move the mouse, click, and type, like the human operator.
The first target is GNOME 46 on Wayland with 3 monitors (Zorin OS 18.1, Ubuntu 24.04 base).

This repository is a fork of `agent-sh/computer-use-linux` (MIT).
Upstream already supplies AT-SPI trees, portal screenshots, RemoteDesktop portal input,
window targeting through a GNOME Shell extension, and an on-screen indicator.
We keep upstream behavior and add what the target machine needs.

## Facts measured on the target machine (2026-10-20)

- Upstream v0.7.20 release binary runs (needs GLIBC 2.39; host has 2.39).
- `screenshot` works through the XDG portal, but the 5760x1080 desktop returns as 1920x360 (`scale` 0.333).
  One monitor at that size is 640 px wide. That is too small for accurate clicks.
- `org.gnome.Mutter.DisplayConfig.GetCurrentState` works and returns the monitor layout:
  DP-2 at x=0, HDMI-2 at x=1920 (primary), HDMI-1 at x=3840, each 1920x1080, scale 1.0.
- RemoteDesktop, ScreenCast, and InputCapture portals are available. Input needs one consent dialog.
- `org.gnome.Shell.Screenshot` and `org.gnome.Shell.Introspect` deny access. Window listing needs the bundled extension.
- `zenity` and `notify-send` are installed.

## Goals

1. Multi-monitor: the agent can list monitors, capture one monitor at native size, and click in monitor-relative coordinates.
2. Safety gate in the server: a policy mode, a kill switch, an audit log, and confirmation for high-impact actions.
   MCP annotations are hints only, and many hosts run with approvals off. The server must enforce the gate.
3. Distribution as `take-my-computer`: README, Claude Code plugin, marketplace, and GitHub release binaries from this fork.

## Non-goals (this version)

- Rename of binaries, crate internals, environment variables, D-Bus names, or the GNOME extension UUID.
  We keep `computer-use-linux*` binary names and `COMPUTER_USE_LINUX_*` variables, so upstream merges stay easy.
  New variables use the `TAKE_MY_COMPUTER_*` prefix.
- Publishing to crates.io or npm.
- A virtual agent monitor or a separate agent session.
- Hit-testing of coordinate clicks against AT-SPI for risk classification.

## Anti-goals

- No silent bypass of the consent dialog (no uinput, no ydotool by default).
- No regression for upstream single-monitor users: without the new parameters, behavior stays the same.

## Part A: multi-monitor

- New module `src/monitors.rs`.
  - On GNOME, read `org.gnome.Mutter.DisplayConfig.GetCurrentState` with zbus.
    Map logical monitors to `{index, connector, x, y, width, height, scale, primary}` in desktop (logical) coordinates.
  - Sort by `(x, y)`. Index 0 is the left-most monitor.
  - Elsewhere, or on error, return one monitor that covers the full capture.
- New MCP tool `list_monitors` (read-only annotations). New CLI subcommand `monitors`.
- New optional parameter `monitor` on `screenshot`, `get_app_state`, and the post-action capture (`screenshot_after`).
  - Accept an index (`0`), a connector name (`"HDMI-2"`), or `"primary"`.
  - Crop the raw capture to the monitor rectangle, then apply the normal size bounds.
    A 1920x1080 monitor returns at 1920x1080 by default.
  - Add `monitor`, `origin_x`, and `origin_y` to the screenshot metadata.
    Desktop x = `origin_x` + preview x / `scale`.
  - A window target and `monitor` together is an error.
- New optional parameter `monitor` on coordinate `click`, `drag`, and `scroll`.
  - When set, `x`/`y` are relative to that monitor's top-left corner, in desktop pixels.
  - Reject coordinates outside the monitor.
  - `monitor` with `relative: true` is an error.
- CLI: `screenshot --monitor <M>` writes the same JSON summary as today.
- Tests: layout parsing from a captured `GetCurrentState` reply, monitor selection, crop rectangle math with scale,
  coordinate conversion, and rejection cases.

## Part B: safety gate

- New module `src/policy.rs`.
- Mode from `TAKE_MY_COMPUTER_POLICY`:
  - `confirm` (default): read-only tools run; low-impact input runs; high-impact actions need confirmation.
  - `full`: all tools run without confirmation. The audit log and the kill switch still apply.
  - `observe`: only read-only tools run. Every mutating tool returns a refusal.
- Kill switch: the file `$XDG_STATE_HOME/take-my-computer/STOP` (default `~/.local/state/take-my-computer/STOP`).
  - While the file exists, every mutating tool returns a refusal and sends no input.
  - CLI subcommands `stop` (create the file) and `resume` (remove it).
  - The README shows how to bind `computer-use-linux stop` to a GNOME keyboard shortcut.
- High-impact classification in `confirm` mode (pure function, unit-tested):
  - `click` or `perform_action` on an element whose accessible name or description matches a commit word:
    send, submit, delete, remove, pay, buy, purchase, checkout, publish, post, transfer, confirm, approve,
    and the Indonesian words kirim, hapus, bayar, beli, terbitkan, posting, setujui, konfirmasi.
    Match whole words, case-insensitive.
  - `press_key` with Return, KP_Enter, or Enter (any modifiers) when the focused or targeted window belongs to an app
    in the send-on-Enter list. Default list: telegram, whatsapp, slack, discord, signal, element, teams, thunderbird, evolution, geary.
    Override with `TAKE_MY_COMPUTER_SEND_APPS` (comma-separated, case-insensitive substrings of app id, wm_class, or title).
  - `type_text` or `set_value` into an element with a password role: refuse in `confirm` mode.
  - `setup_accessibility`, `setup_window_targeting`, and `run_shell`.
- Confirmation channel, in this order:
  1. MCP elicitation, if the client declared the elicitation capability.
  2. A desktop dialog with `zenity --question`, with a 60-second timeout.
  3. Otherwise refuse, and tell the agent which mode allows the action.
  The dialog text shows the tool, the target app and window title, the element name, and the key or a text length.
  It never shows typed text in full.
  While the server waits, the agent's tool call is blocked, so the same agent cannot answer the dialog.
- Input lock: hold an exclusive `flock` on `$XDG_RUNTIME_DIR/take-my-computer-input.lock` during each mutating call,
  so two agents cannot interleave input inside one action.
- Audit log: append one JSON line per mutating call to `$XDG_STATE_HOME/take-my-computer/audit.jsonl`.
  Fields: time, client name, tool, mode, tier, decision, target app, window title, element name, key,
  text length and SHA-256 (never the text), result `ok`.
- New read-only MCP tool `policy_status`: mode, kill switch state, send-on-Enter list, audit log path.
- Tests: classifier cases, mode decisions, kill switch, audit record shape (no plain text).

## Part C: distribution as take-my-computer

- README: a new top section that names `take-my-computer`, credits upstream, lists what differs, and shows install steps.
  Keep the upstream README content below it.
- `LICENSE`: keep the upstream copyright line. Add a line for Rama Aditya.
- Claude Code plugin and marketplace: name `take-my-computer`, owner `RamaAditya49`,
  download base `https://github.com/RamaAditya49/take-my-computer/releases/download/v$version`.
  The MCP server entry name is `take-my-computer`.
- Version `0.7.20-tmc.1` in `Cargo.toml`, `package.json`, and the `tool_handler` attribute.
  `scripts/mcp_safety_check.py` must still pass.
- CI: keep the checks and the release-binary job. Disable crates.io and npm publishing in this fork.

## Build and verification

- Build and test on a separate build host, not on the desktop that the tests control.
  Use a `rust:1-bookworm` container (glibc 2.36), so the binaries run on Ubuntu 24.04.
- Gates per part: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`, `cargo test --locked`,
  and `python3 scripts/mcp_safety_check.py` when tool metadata changes.
- Live checks on the desktop (short CLI runs only): `monitors`, `screenshot --monitor 1`, `policy_status`,
  kill switch refusal in `observe` mode. Input checks wait for the desktop user, because the portal shows a consent dialog.

## Left to the builder

- Exact Rust structure inside `server.rs`, as long as each mutating tool passes through the gate before any input.
- How `monitor` threads through the existing capture and crop code.
- Elicitation API details in rmcp 3.5.1.
